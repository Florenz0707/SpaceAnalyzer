# M1–M4 验证记录

## 当前结论

2026-10-30，在 `feat/snapshot-core` 中实现了快照业务服务、HTTP 接口与 Canvas 可视化，完成下述规模测量及补充回归。**真实符号链接与取消终态刷新两项阻塞均已解除，M1–M4 实现及工程验收完成，保留功能分支供用户体验确认。**

原符号链接创建曾遇到 WinError 1314；用户已手动创建合成链接，随后普通用户进程完成真实 SymbolicLink 验收：不跟随目标、累计 0 字节、记录 reparse_point、拒绝链接根及含链接的祖先路径，目标元数据保持不变。原始结果见 `benchmarks/symbolic-link.json`。

取消接口立即返回 cancelled 时未刷新历史或打开部分快照的问题，已在用户授权后修复并通过原失败用例和补充回归；详见 [CANCEL-ACCEPTANCE.md](CANCEL-ACCEPTANCE.md)。功能分支已按任务分别本地提交，尚未合并，不执行 push 或 pull。

最终完整检查全部通过：14 项后端 pytest（含显式启用的真实符号链接集成测试）、9 项前端 Vitest，以及 Prettier、markdownlint、Ruff、ESLint、Pyright、Python 编译和生产构建。修复前失败用例保留，并已转为通过。

## 已验证的业务行为

- 合成目录的层级、空目录、零字节文件、中文与空格路径、已知逻辑大小汇总。
- SQLite 持久化、重新打开服务、历史结果不随源文件后来变化而自动更新。
- 自身数据库与 WAL/SHM/journal 文件排除、有界分页、非法路径和未知 ID。
- 模拟权限错误时保留部分结果，公开查询能读取错误及“不完整”状态。
- 单扫描任务、重复启动拒绝、取消幂等、受控子进程中断后的恢复。
- 针对自建文件的正文打开拦截与大小、修改时间、模式比对；没有扫描用户真实目录。
- HTTP 合约、本机 Host/Origin 限制、扫描阻塞时健康检查和查询仍响应、并发启动返回 409。
- 前端静态托管、SPA 回退、未知 API 与静态资源仍返回 404。
- 布局面积权重、边界与无重叠；React 下钻、返回、详情、后端断线提示和历史列表重试。

已补齐并通过扫描中文件消失、硬链接按目录项计数、跨快照节点拒绝和真实符号链接验证；取消立即终态、异步取消、取消失败，以及断线重试返回运行态或终态的交互测试也通过。

## 性能数据与口径

环境：Windows build 26100（Python 平台字符串为 Windows-10-10.0.26100-SP0），Intel64 Family 6 Model 186 Stepping 2，20 个逻辑处理器，Python 3.11.5，Node.js 22.16.0，Headless Chrome 156。

下列文件系统测试实际创建并扫描一字节合成文件，没有直接向数据库灌入节点。生成耗时与扫描耗时分开；查询为同一根目录的 20 次查询。数据集只代表这台机器的这些情况，不构成整盘扫描或其他硬件的性能保证。

| 数据集                                    | 生成时间 | 扫描时间 | 查询中位数 / p95   | 进程生命周期峰值工作集 | 数据库大小 |
| ----------------------------------------- | -------- | -------- | ------------------ | ---------------------- | ---------- |
| 单目录 100,000 文件，首次                 | 22.95 s  | 2.724 s  | 12.244 / 13.738 ms | 33.16 MiB              | 28.15 MiB  |
| 单目录 100,000 文件，保留数据库供 UI 验证 | 19.36 s  | 2.743 s  | 12.098 / 12.736 ms | 33.16 MiB              | 28.15 MiB  |
| 128 层，128 文件、129 目录                | 0.047 s  | 0.043 s  | 1.519 / 1.619 ms   | 30.60 MiB              | 148 KiB    |

峰值内存来自 Windows GetProcessMemoryInfo，范围包含进程启动及合成数据生成，不能解释为“扫描增量内存”。所有上述扫描均为 completed、0 个扫描错误。

### 布局与绘制

公开布局函数在 Node.js 中单独测量 20 次，纯算法数据与真实浏览器视图分开记录：

| 项数    | 布局中位数 | 布局 p95  |
| ------- | ---------- | --------- |
| 200     | 0.120 ms   | 0.590 ms  |
| 1,000   | 0.481 ms   | 0.657 ms  |
| 100,000 | 20.294 ms  | 45.944 ms |

浏览器加载真实十万文件快照，200 行数据，其余及过小条目合并为“其他”。由于文件均为一字节，最终只绘制 1 个聚合矩形；20 次交替视口宽度采样的布局时间返回 0（低于可观察分辨率，不能解释为零成本），Canvas paint 中位数 0.200 ms、p95 0.300 ms。该 paint 仅测 CPU 绘制命令提交，不含 GPU 完成时间；不能把此结果当作 200 个可见矩形或十万个矩形的绘制耗时。

浏览器采样时 JS heap 约 4.72 MiB，是瞬时读数，不是浏览器总内存或峰值。原始结构化结果见本目录 `benchmarks/`。百万节点只是后续压力目标，尚未测量。

## 复现

先按 COMPOSE 安装依赖，在功能工作树根目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check.ps1
uv run --project backend --frozen python -m spaceanalyzer.benchmark --shape wide --count 100000 --output .cache/benchmarks/wide.json
uv run --project backend --frozen python -m spaceanalyzer.benchmark --shape deep --count 128 --output .cache/benchmarks/deep.json
```

基准只生成自己的临时目录并在结束时清理，不接受用户目录作为扫描目标。`--keep-database .cache/benchmarks/wide.sqlite3` 可保留合成快照数据库用于浏览器检查；默认不保留临时数据。

普通测试仅使用很小的合成基准验证入口正确性，不在每次提交时创建十万文件。实际目录扫描、数据库查询、算法测量和浏览器 paint 的证据不得互相替代。
